Final sweep: legacy vs fixed-output 16, 32, 48, 64 KB

One dataset, one build, one node. The table is iouring_bench.readbench: about 203 GB logical, 64 M single-row partitions, roughly 0.45-compressible under Zstd level 8, BIG format, LCS, XFS on /dev/nvme0n1p8. Read path is disk_access_mode=standard, buffered, on a 16 KB page kernel. Key, row, and chunk caches are off; heap is 16 GB; autocompaction is off. The node runs with io_tracking.enabled and set_sep_thread_name, so the per-read server histograms populate. Fixed-output uses the Zstd streaming packer with tight fill. Rewrites ran with upgradesstables -j 0 across all 10 compaction threads. Each arm has two warm modes. SLO uses --maxrlat 50 at 32 threads and reports throughput at a latency target. SAT uses a fixed 140 k offered rate at 64 threads and drives the system to saturation. Every value below is the measured figure from the raw traces. Findings were verified by an adversarial review pass.

Each arm has a distinct advantage over the legacy 64 KB baseline. The two middle arms are the strongest practical choices and are easy to miss in the detail tables, so they are called out here.

3. Per-query IOPS across the sweep

This is the metric that caused confusion in an earlier draft. read_iops counts pread syscalls per read command. It is recorded in ReadIOContext.physicalReadOps, incremented on every ChannelProxy.read. It is not the device read count. The value for one read command is the sum of every pread across every sstable the partition touches. For a fully-compacted key that is one buffered index-scan pread plus one data-chunk pread, so the typical value is 2. The tail reaches 8 to 10 for keys matched in several live sstable generations or keys landing far from a Summary sample, which lengthens the index scan across extra buffer refills. Point reads disable read-ahead, so read-ahead is not a factor here.

Interpretation

The win is bytes per read, not read-op count. Device reads per request near 2 to 3, the Data.db 1 plus Index.db 2 split, and server read_iops at p50 2 are all S-independent. Every arm issues the same handful of reads. Fixed-output changes the bytes each read moves. Device KB/op falls 57% at S=16.

Throughput is limited by CPU and is equal across arms on this machine. The client and server share 10 cores. SAT throughput is flat within noise from 104 to 112 k while CPU sits at 88 to 96% and device utilization is only 47 to 56%, so the device is half idle. Byte savings would convert to throughput on a device-bound machine, not here. What they buy here is headroom. The SAT error rate rises with chunk size from 0% at fo-16 to 6.2% at fo-64. Throughput is also run-variable: legacy SLO measured 61.6 k here and 52.4 k in an aborted earlier run at the same config.

Recommendation

S=32 is the balanced default. It costs 0.7% more on disk and cuts device bytes per op by 32% with clean errors. S=16 is the choice when maximizing the read-byte reduction, at 57% fewer device bytes and 7.6% more on disk; pairing it with a Zstd dictionary would recover most of that on-disk cost. S=48 is a modest free point that is smaller on disk than legacy by 1.8% and still 6% fewer device bytes. S=64 should be avoided for point reads. It over-fetches 19% more than legacy and has the worst error profile under load.

Caveats and method

  • The typical per-query read count is 2, measured as read_iops p50. An earlier draft reported the histogram max of 10 as if it were the typical value. That was wrong and is corrected in section 3.
  • read_iops counts pread syscalls, which is a different metric from device reads. Device reads are about 2 to 3. Preads are greater than or equal to device reads because cache-served preads do not reach the disk.
  • The bytes_decompressed p50 is a reservoir or recording artifact and is not trusted. It is not fixed-output-specific, since legacy shows the same zero p50 under warm load.
  • The fo-64 warm SLO run is excluded as capacity because it overloaded at 4.84% errors. SAT latency is invalid wherever errors are elevated.
  • Cold device KB is read-ahead-inflated and quantized to 16 KB pages. The clean cold signal is VFS KB per request, which equals S plus 16.
  • Throughput and latency are CPU-bound and run-variable. The robust signals are device bytes per op, on-disk ratio, and read counts.
  • The client and server share one 10-core machine, so byte savings would show as throughput on a device-bound machine, not on this one.
  • The chunk_cache_hits_per_read and chunk_cache_misses_per_read histograms are excluded. They have no producer call site and the chunk cache is disabled in this configuration, so they always read 0.
  • Per-component page-cache hit-rate figures went negative in places, for example Data.db at −22%. Those are mm_filemap sampling artifacts and are not quoted as rates.
