Compressible data — legacy 64 KB vs fixed-output 16 KB

Re-run on a regenerated compressible dataset (SSTableGen value profile changed: unique random head + shared-dictionary tail → Zstd@8 ratio ~0.45, matching production, vs the earlier incompressible ~1.0). 64 M single-row partitions, ~198 GB logical. Both configs: BIG format, LCS (offline-releveled), autocompaction off, disk_access_mode=standard (buffered), caches off, 16 GB heap. Legacy is the SSTableGen default (chunk_length_in_kb=64); fixed-output is compressed_chunk_length_in_kb=16. So this is a default→optimized comparison that combines chunk-size reduction (64→16) with block alignment.

Reading the results

The device-read win is much larger on compressible data than it was on incompressible. Cold device bytes/request drop 64% (112→40 KB) and warm device bytes/op drop 57% (25.8→11.0). The reason: a 64 KB legacy chunk must be read and decompressed in full to return one ~3.1 KB value, and on a cold read the buffered fetch plus readahead touches ~112 KB of device. A 16 KB fixed-output block is one aligned read (~16 KB) plus the index — so the over-fetch that a large chunk causes is largely eliminated. That efficiency also lifts warm throughput +28% (52.4k→67.3k ops/s, 0 errors) — each request moves less device IO, so the node sustains more of them.

The cost is on-disk size: +9% (ratio 0.449→0.492). This is new — on incompressible data the ratio was ~1.0 either way, so there was no size cost. On compressible data, smaller compression chunks give Zstd less context to find matches, so 16 KB chunks compress worse than 64 KB. Most of the +9% is this chunk-size effect (64→16), not fixed-output framing itself: the incompressible run measured fixed-output framing+padding at ~2.3%, so a like-for-like legacy-16 KB vs fixed-output-16 KB comparison would show only that ~2–3% overhead, with the rest of the 9% being the context loss shared by any 16 KB scheme.

Two caveats. (1) This compares 64 KB legacy to 16 KB fixed-output, so it bundles chunk-size reduction with alignment (the realistic default→optimized move; a like-for-like 16 KB-vs-16 KB run would isolate alignment). (2) The warm avg/p99 latency is higher for fixed-output (48 ms / 633 ms vs 9 ms / 176 ms) while p50 is the same — the adaptive limiter let fixed-output run at a higher sustained load (67k vs 52k ops/s), and the cold-miss tail grows with load; a controlled equal-offered-rate run would be needed to separate load-level from any per-read tail cost (the same kind of artifact the heap/maxrlat investigation earlier surfaced).

Conclusion: On realistic ~0.45-compressible data, fixed-output-16 KB cuts device bytes per read by ~57–64% and raises throughput ~28% versus the 64 KB legacy default, at a cost of ~9% more on-disk size (mostly the smaller-chunk compression-context loss, not fixed-output framing) and a higher warm latency tail at the elevated load it enables. The bytes-per-request win — the project's target — is larger here than on incompressible data; the on-disk trade is the new consideration compressible data introduces, and is tunable via the chosen block size.
