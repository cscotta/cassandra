Block-aligned compressed chunks — before / after

Apache Cassandra, branch cscotta/io_opto. Table iouring_bench.readbench (~188 GB, 64 M rows, incompressible values), ZstdCompressor level 8, LeveledCompactionStrategy, raw XFS /dev/nvme0n1p8, disk_access_mode=standard (buffered), chunk cache off, 16 KB kernel pages. Device metrics from eBPF (block_rq_complete), latency from easy-stress HDR.

The change

Before (legacy): compression fixes the uncompressed input per chunk (chunk_length_in_kb=16). Compressed chunks are variable-sized and packed back-to-back, so a chunk lands at an arbitrary byte offset. A ~16 KB chunk at an unaligned offset spans two 16 KB pages → the device reads 32 KB to return one chunk.

After (fixed-output): a new opt-in mode (compressed_chunk_length_in_kb=16, max_uncompressed_chunk_length_in_kb=128) fixes the compressed on-disk size to a block-aligned S=16 KB, packing a variable amount of input into each block. Chunk i lives at offset i×S, so a read is one aligned S-byte device IO with no page straddle.

3. On-disk size — the cost

Fixed-output pads each block to S and adds per-block framing (length prefix + CRC). The initial +12% was dominated by buffer-boundary partial chunks (the write buffer was sized to the 128 KB cap, so each flush ended in one short, mostly-padded chunk). Phase 5 decoupled the write buffer (now ~2 MB, holding ~128 chunks per flush) so boundary partials are rare — on-disk overhead dropped to +2.3% and ~20 GB was reclaimed. The residual ~2.3% is per-block framing plus the packer's ~256-byte accept-first-fit margin (which keeps writes at ~one compression per chunk on incompressible data).

4. No CPU regression — JFR

A JFR profile (settings=profile) under a steady fixed-rate load showed read-path CPU dominated by generic work (partition-index binary search 547 samples, token compare, row-index-entry lookup, iterators, metrics). The fixed-output-specific CompressionMetadata.fixedChunkIndex was 88 samples (~0.7%) and uncompressFixedBlock did not appear in the top 30. An earlier warm run showed 44–75% errors; that was traced to the 500 MB heap OOM-ing under the load generator's ~100 k ops/s offer — raising the heap to 16 GB gave 0 errors. There is no per-read CPU cost from the feature.

Correctness

Reads return correct data end-to-end at 200 GB scale (verified across the key range). FixedOutputCompressionTest passes 5/5 (round-trip of incompressible / compressible / sub-chunk data, sequential + random access, config validation, streaming fail-fast). 39 legacy compression tests still pass; build, checkstyle, and rat are clean. A deep review found and fixed 7 issues (streaming guard, buffer sizing, mmap routing, FSWriteError, validation bounds, and two low-severity items).

Bottom line

The optimization delivers its target — fewer device bytes per read: −33% cold (the data chunk becomes a single aligned page instead of a two-page straddle) and −13% under warm load, with no CPU or correctness regression. After the Phase 5 write-buffer decouple, the on-disk cost is ~2.3% (down from ~12%). Streaming/repair of fixed-output sstables is gated off (fails fast) pending Phase-4 receiver work.
