Phase 7 — reducing the partition-index read (the second IOP)

Context: after fixed-output compression, a cold point read on iouring_bench.readbench still issues two device reads — the data chunk (now one aligned page) and the partition-index lookup. Phase 7 targets the index read. Grounded in this cluster: BIG format (pa), only Data.db is compressed; Index.db = 1.26 GB (uncompressed primary index), Summary.db = 14 MB (samples), Filter.db = 43 MB (bloom); and both key_cache_size and row_cache_size are 0 MiB — so every read measured takes the full index-miss path.

The two IOPs today, and which one Phase 7 targets

A cold point read on BIG does, in order:

  1. Bloom filter (Filter.db) — in memory, no device read.
  2. Index summary (Summary.db) — in memory; a binary search gives an approximate offset into Index.db plus the sampling interval. (This is the AsymmetricOrdering.binarySearchAsymmetric the JFR showed — it is in-memory.)
  3. Primary index read (Index.db) — seek to the summary's offset and read forward, deserializing entries until the exact key is found, yielding a RowIndexEntry (the data-file position). ← device read #1, the index IOP Phase 7 targets.
  4. Data chunk (Data.db) at that position. ← device read #2, now one aligned page after fixed-output.

The index read costs a full page (~16 KB in the standard-mode measurement) to locate a ~tens-of-bytes entry: Index.db is uncompressed and read through a buffered/mmap reader that fetches a page/buffer covering up to min_index_interval (default 128) entries, then scans. So it over-fetches — the same shape as the data-chunk straddle we already fixed, but caused by read-buffer/page granularity, not compression.

How the index reads would change under Phase 7

(a) Key cache — eliminate the index read on hits

The key cache maps (sstable, key) → RowIndexEntry (the data position) in heap. On a hit, step 3 is skipped entirely and the read goes straight to Data.db, so a cold-but-cached read drops from 2 IOPs → 1 IOP. This is a config lever (re-enable/size the key cache; it is 0 here) plus minor code to ensure fixed-output sstables populate/consult it normally. Caveat: it only helps the working set — a uniform-random scan over 64 M keys will not fit, so the miss path is unchanged. This is the biggest win for real (skewed) workloads.

(b) Right-size / align the miss-path index read

Even on a cache miss, the ~16 KB fetched for a small entry is over-fetch. Two ways to shrink it:

  • Denser index summary (lower min_index_interval): the summary points closer to the exact entry, so the scan window — and the read — is smaller. Trades Summary.db memory (14 MB now) for a smaller Index.db read.
  • Aligned / right-sized index read: read only the needed region, block-aligned (e.g. 4 KB under O_DIRECT, or a smaller index reader buffer) instead of a 16 KB page — the same alignment idea as the data chunk, applied to the index reader.

Effect: the index device read shrinks from ~16 KB toward ~4 KB, so a cold miss goes from 32 KB → ~20 KB device bytes (data 16 KB + index ~4 KB) — still 2 IOPs, but fewer bytes.

(c) Structural options (larger changes, on-theme with fixed-output)

  • Compress + fixed-output-align Index.db. It is uncompressed today; giving it the block-aligned treatment would make index reads single aligned blocks like the data. Bigger change (a new compressed index component).
  • BTI format (trie-indexed sstables): replaces Index.db + Summary.db with a page-aligned trie (-Partitions.db/-Rows.db) walked with page-aligned reads — designed for fewer, smaller index reads. A format migration (BIG → BTI), orthogonal to compression; the branch could combine BTI indexing with fixed-output data.

Why this matters most under io_uring / mmap

Phase 6 showed that under io_uring mode the index is served by mmap, and a cold fault pulled ~1 MB of readahead — dwarfing the 16 KB data chunk. So on the branch's target (O_DIRECT data) path, the index is the dominant cold cost, and Phase 7's index work (align/right-size the index read, route the index through the aligned reader instead of mmap-with-readahead, or the key cache) is where the next large reduction is.
