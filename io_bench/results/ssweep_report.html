Fixed-output S-sweep — 16 / 32 / 48 / 64 KB vs legacy 64 KB

Same table iouring_bench.readbench (~203 GB logical, 64 M single-row partitions, ~0.45-compressible), all points rewritten and measured on the same build and node: BIG format, LCS, Zstd@8, raw XFS, disk_access_mode=standard (buffered, 16 KB pages), key/row caches off, 16 GB heap, autocompaction off. Fixed-output uses the tightened packer (accept threshold 63/64, 16 MiB flush buffer). S values are all whole 16 KB pages (24 KB is excluded — 1.5 pages would straddle and reintroduce the over-fetch the feature removes). Legacy = plain chunk_length_in_kb=64. Findings were adversarially verified against the raw traces before publication; robust vs confounded metrics are separated below.

Overhead falls monotonically as S grows — larger blocks pack more uncompressed input (a bigger Zstd window), so ratio improves. Padding is ~1.5% at every S with the tight packer, so this axis is pure compression context, not framing. On-disk overhead crosses +2% at S ≈ 29 KB: any S ≥ 32 KB stays within 2% of legacy, and S ≥ 48 KB is smaller than legacy.

Device bytes/op (what actually reaches the disk) is the primary efficiency signal: it falls monotonically as S shrinks and beats legacy for every S ≤ 48 KB, crossing the legacy 24.9 KB line at S ≈ 50 KB. Device reads/op (IOPS) is below legacy at every S (0.38–0.44 vs 0.47) — alignment turns legacy's straddled chunk fetch into one aligned block read regardless of S. Cold VFS KB/req = S + 16 KB exactly (one data block + one index page), the clean cold read-size measure.

Caveat on absolute device bytes. The absolute KB/op level inherits the page-cache state of the run (see §3) — a hotter or colder cache shifts it. Read it as a relative cross-S trend, not a fixed device budget. Also note VFS KB/op (bytes the DB reads, cache-served included) beats legacy (23.4) only at S=16 (17.0); it is higher for S ≥ 32. Device is what reaches disk, so device is the metric to headline.

3. Throughput, latency, cache hit — CONFOUNDED, not comparable across S

These are shown for completeness but must not be read as cross-S efficiency results. The adaptive --maxrlat 50 limiter settled at different offered rates driven by the page-cache hit fraction, which itself moves only because larger blocks enlarge the working set. If the runs were device-bandwidth-bound, ops/s × KB/op would be constant — instead implied device throughput rises 718→981→1239 MB/s across S16/32/48, and S16 ops/s even exceeds legacy, which is impossible under a fixed device ceiling. p99 also overshoots the 50 ms target 2–4× (bimodal: ~0.3 ms cache hits vs tens-of-ms misses), so latency figures are tail/limiter statistics, not steady service times.

4. The tradeoff and recommendation

S is a single dial trading on-disk size against device bytes per read, in opposite directions, with the alignment IOPS reduction holding at every S:

Son-disk vs legacywarm device KB/op vs legacycharacter
16 KB+6.9%−56%max read-byte win, storage cost
32 KB+1.0%−30%balanced sweet spot
48 KB−1.5%−3%space-positive, marginal read win
64 KB−2.0%+23%on-disk-optimal, read-negative
Recommendation by objective.
  • Balanced (recommended default): S = 32 KB. +1.0% on-disk (inside a 2% budget) for a ~30% cut in device bytes/op and fewer device reads/op. Best overall trade for a ~0.45-compressible point-read workload.
  • Maximum read reduction: S = 16 KB. −56% device bytes/op and the smallest cold read (32 KB), at +6.9% on-disk. Choose when read-amplification/latency matters more than ~7% storage — or pair with a Zstd dictionary to claw back most of that 7% (compress/decompress already compose; only the trainer needs the fixed-output fix).
  • Storage-conservative: S = 48 KB. Actually smaller than legacy (−1.5%) while still edging below legacy on device bytes (24.2 vs 24.9) — but the read win is marginal.
  • Avoid S = 64 KB for point reads: best on-disk but a 64 KB block over-fetches vs legacy's ~29 KB compressed chunk, so device bytes go up +23%.
The useful space-neutral window is roughly S ∈ [30, 48] KB: below ~29 KB you pay storage for a larger read cut; above ~50 KB you lose the device advantage. Every S ≤ 48 KB beats legacy on device traffic and on device-read count.

Caveats

  • Throughput, latency, and cache-hit are limiter/working-set confounded and excluded from cross-S efficiency claims (§3).
  • Warm device KB/op is robust as a relative trend; its absolute level depends on cache state.
  • Cold device KB (n=20) is noisy with multi-block outliers and non-monotonic — cold VFS KB (= S+16) is used instead.
  • Ratios for S=16/32/48 are computed from measured space over the fixed ~203 GB logical size; S=64 and legacy are direct tablestats readings.
  • Write cost rises at small S with the current multi-trial packer; the pending Zstd streaming override (Task #19) would restore ~1 compression/chunk.
