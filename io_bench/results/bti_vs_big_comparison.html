BIG vs BTI SSTable format — read comparison (both fixed-output)

Same table iouring_bench.readbench (~200 GB, 64 M single-row partitions, incompressible), fixed-output S=16 KB data compression on both (Data.db identical), Zstd@8, LCS, raw XFS, disk_access_mode=standard (buffered), caches off, 16 GB heap. Only the SSTable index format differs: BIG (Index.db + in-memory Summary.db) vs BTI (a page-aligned trie in Partitions.db). Rewrote BIG→BTI via upgradesstables -a; BTI+fixed-output reads verified correct (5/5 across the key range).

BTI is worse cold. A fully-cold point lookup walks the trie root → internal → leaf on Partitions.db — several page reads — plus the data chunk (4 device reads, 52 KB). BIG resolves the position with an in-memory Summary.db binary search and a single Index.db read, then the data chunk (2 reads, 32 KB). Because cold_readbench drops caches before every read, the entire trie path is cold every time — the trie's worst case.

Warm is a trade, not a win. Same throughput (~67.4k, 0 errors) and same median latency (cache-hit fast path). BTI reads ~8% fewer device bytes (its 55%-smaller index caches better, so fewer index misses reach disk) — but it issues ~2× the preads (2.71 vs 1.26/op: the trie walk is several node reads, mostly served from page cache) and pays for that in CPU: avg latency 15.9 ms vs 9.3 ms and p99 440 ms vs 176 ms. BTI shifts index cost from disk bytes onto syscalls/CPU.

Interpretation — this corrects the Phase 7 hypothesis

The Phase 7 premise was that BTI would reduce the index IOP. For this workload it does the opposite: BTI reduces index size (−55%) but increases index read count for cold point lookups (a multi-level trie walk vs one summary-guided read), and adds per-op CPU/latency warm. The data-chunk win from fixed-output is unchanged (Data.db is identical). Net for a uniform-random, single-row-partition, cold point-read profile: BIG + fixed-output is better than BTI + fixed-output.

What this microbenchmark does not exercise — and where BTI is designed to win: range scans (trie walks amortize over many rows), wide partitions (the Rows.db row-trie, empty here), memory-constrained nodes and hot working sets (the 55%-smaller index caches far better), and workloads where the upper trie stays resident so lookups touch only a leaf + data. Our p50 (0.39 ms) already shows that when the trie is hot the fast path is equal to BIG; the penalty is on the cold/tail reads that a uniform-random scan over 64 M keys keeps producing.

Conclusion: Fixed-output composes cleanly with BTI (correct, ratio retained, index halved), but BTI does not help — and slightly hurts — this cold uniform-random point-read benchmark, because the trie walk costs more read IOPs than BIG's summary + single index read. Keep BIG + fixed-output for this profile; choose BTI for scan-heavy, wide-partition, or memory-constrained workloads. The remaining index-IOP lever for point reads is caching (key cache to skip the lookup on hot keys) or right-sizing/aligning the index read — not the index format.
