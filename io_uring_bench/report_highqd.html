io_uring vs. FileChannel — high queue depth, warm & cold

JMH throughput at queue depth 128 across 4 threads. io_uring (FFM binding) keeps QD I/Os in flight per thread; FileChannel issues blocking calls (one in flight per thread). Higher is better.

With the page cache bypassed (O_DIRECT) and a deep queue, io_uring wins the read workloads — up to 6.39× the throughput of blocking FileChannel (random reads, 4 KiB). On cold 4 KiB random reads, io_uring's edge grows from 1.01× at QD 1 to 16.02× at QD 256. This is the device-bound, high-concurrency regime io_uring is built for; on a warm page cache (below) it still loses, because there is no device latency to overlap.
Two regimes, same code. WARM = buffered I/O, the 512 MiB file resident in a 62 GiB page cache (no device access). COLD = O_DIRECT on both sides (page cache bypassed, posix_fadvise(DONTNEED) in setup), every read hitting the NVMe. Both sides run 4 threads; the io_uring side additionally keeps QD=128 operations in flight per thread (4×128=512 outstanding), while a blocking FileChannel has one in flight per thread — which is exactly the asymmetry io_uring exists to exploit and the reason it needs a device-bound workload to win. Writes are not fsync'd. Error bars are JMH 99.9% CIs.

Cold random reads: throughput vs. queue depth

4 KiB O_DIRECT random reads, single thread. io_uring keeps QD I/Os in flight per thread; blocking FileChannel can only have one, so it flatlines while io_uring scales with the device.

Cold cache — O_DIRECT (device-bound)

Page cache bypassed; every read reaches the NVMe. io_uring overlaps device latency across the deep queue.

Warm cache — buffered (page cache)

Data resident in RAM; this measures per-op mechanism overhead, where io_uring cannot win.
