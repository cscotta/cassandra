Fixed-Output Block-Aligned Compression for Apache Cassandra

Design and evaluation of a block-aligned compressed-chunk mode for the SSTable read path, branch cscotta/io_opto. This document covers the objective, the design, the benchmark methodology, the evaluation criteria, and the measured results.

1. Objective

Reduce the device IO a single-partition read spends on the compressed data file, and measure that reduction with per-read instrumentation. A compressed chunk in Cassandra lands at an arbitrary byte offset in Data.db. When the chunk is smaller than or unaligned to the device or page granularity, a read of that chunk pulls extra bytes off the device. The objective is to make each compressed chunk occupy a fixed, block-aligned on-disk size so a chunk read is one aligned device transfer, without an increase in on-disk size and without breaking the SSTable format or the streaming protocol.

2. Problem statement

Two forms of over-fetch appear on the read path.

  1. Alignment straddle. A compressed chunk that is not aligned to the page size spans two pages. A buffered read of that chunk faults both pages. On the 16 KB page kernel used for this work, a 16 KB compressed chunk at an unaligned offset materializes two pages.
  2. Chunk granularity. To return one small value the reader must read and decompress the whole chunk it lives in. A 64 KB uncompressed chunk holds about twenty 3.1 KB values, so a read of one value pulls the entire chunk.

The default compression stores a fixed uncompressed input size per chunk and a variable compressed output size, so the compressed offset of a chunk is not aligned to any device boundary. The direct and io_uring readers already align the compressed offset down and over-read the delta for this reason. The design target is to remove the delta by fixing the on-disk chunk size.

3. Goals and non-goals

Goals

  • Each compressed chunk occupies a fixed on-disk size S that is a whole number of device blocks, so a chunk read is one aligned transfer with zero over-read delta.
  • No round-up padding scheme. Pack a variable amount of input into each chunk until the compressed output fills S, leaving only a small sub-block tail.
  • On-disk overhead stays low relative to the default compression.
  • Write-time recompression stays close to one compression per chunk.
  • The mode is opt-in per table and is off by default.

Non-goals and constraints

  • No SSTable format version bump. Legacy SSTables stay byte-identical and the mode is self-describing.
  • No messaging or streaming protocol version bump. Peers that do not understand the mode reject it rather than corrupt data.
  • The default fixed-input compression path is unchanged.

4. Design and approach

4.1 On-disk format

Every chunk occupies exactly S bytes on disk, aligned to a block boundary. The block layout is a 4-byte payload length, the compressed payload, a 4-byte CRC32 over the payload, then zero padding to S. The framing is 8 bytes per block. S is configured by the compression option compressed_chunk_length_in_kb and must be a multiple of the 4 KB alignment floor. A second option, max_uncompressed_chunk_length_in_kb, caps the uncompressed input packed into one chunk so the decompression buffer is bounded.

4.2 Metadata and self-describing mode

Because the compressed size is now fixed, the compressed offset of chunk i is implicit at i times S. The metadata therefore stores the uncompressed cumulative offset table instead of the compressed offset table, which is comparable in size. chunkFor(position) binary-searches the uncompressed offsets rather than dividing by a fixed chunk length. The mode is recorded as reserved marker keys in the -CompressionInfo.db option map, so an SSTable declares its own mode and no format version changes. The messaging serializer carries the same markers, so a streamed SSTable is self-describing on the receiver.

4.3 Pack-to-fill compressor API

A new method ICompressor.compressBounded(input, output, maxOutputLen) compresses a prefix of the input so the output fills close to maxOutputLen, and returns the number of input bytes consumed. The default implementation compresses a candidate prefix directly into the output, accepts the first prefix that fits, and grows the prefix only when the output is under-filled. For incompressible data this is one compression per chunk. For compressible data it grows across a few trials.

4.4 Zstd streaming override

The default multi-trial path recompresses overlapping prefixes from scratch, which costs three to six full compressions per chunk on compressible data. ZstdCompressorBase overrides compressBounded with a streaming implementation. It feeds input into one Zstd frame through ZstdCompressCtx.compressDirectByteBufferStream, flushes after each feed to observe how full the output is, then closes the frame with an end directive. This packs a chunk in roughly one forward pass over the consumed input. The dictionary-aware subclass loads the trained dictionary into the same streaming context.

A streaming frame built incrementally does not know its total size when the header is written, so it carries no content-size field. The one-shot Zstd decompress path needs an exactly sized destination in that case. The reader was changed to size the decompression buffer to each chunk's exact uncompressed length, taken from the metadata offset table through CompressionMetadata.fixedOutputUncompressedLength. This is correct for frames that do carry a size as well.

4.5 Packer tightening

Two write-path constants govern padding. The accept threshold decides how full a block must be before the packer stops growing, and the write buffer size governs how often a flush emits a short trailing block. Raising the accept threshold from 15/16 to 63/64 and the flush buffer from 2 MiB to 16 MiB raised the average block fill from 93.6% to 98.6% and cut padding from 6.4% to 1.45%, with no change to the on-disk format and no effect on reads. These are the two padding sources that appeared when the compressible data was measured.

4.6 Reader and rebufferer

The reader reads exactly S bytes at i times S, which is one aligned device transfer with a zero over-read delta on the direct and io_uring paths. Decompression reads the payload length from the block header, verifies the CRC over the payload, and decompresses into a buffer sized to the chunk's exact uncompressed length. A variable-chunk rebufferer derives the chunk base from chunkFor rather than masking by a power of two, and sizes its buffer to the observed maximum uncompressed chunk length rather than the configured cap.

4.7 Streaming and repair receiver

Fixed-output SSTables stream and repair. The wire CompressionInfo carries the per-chunk uncompressed offsets and the mode markers. The receiver parses the fixed block layout, verifies the embedded CRC, and places chunks by the streamed uncompressed offsets rather than a fixed stride. A peer that does not understand the mode rejects the unknown compressor options rather than misplacing chunks.

5. Instrumentation and benchmark methodology

The read path was instrumented so a benchmark can attribute IO at four levels. The measurement machine is a single node with an XFS data disk on an NVMe partition, a 16 GB heap, and buffered reads on a 16 KB page kernel. The workload is 64 M single-row partitions, about 203 GB logical, roughly 0.45-compressible under Zstd level 8, LCS, with key, row, and chunk caches off.

The server histograms require the node to start with io_tracking.enabled and set_sep_thread_name. The counter read_iops is recorded in ReadIOContext.physicalReadOps on every ChannelProxy.read, so it counts pread syscalls per read command and includes reads served from the page cache. It is not the device read count.

Each arm runs three phases. A cold phase issues isolated reads with the page cache dropped before each. A warm SLO phase runs at 32 threads under an adaptive 50 ms p99 latency target. A warm saturation phase runs at 64 threads with a fixed 140 k offered rate to drive the system past its knee. The saturation phase exists because the SLO target throttles offered load and leaves CPU and device utilization far below full, which understated the achievable throughput in earlier runs. Rewrites between arms run with upgradesstables -j 0 across all 10 compaction threads.

6. Evaluation criteria

  • On-disk compression ratio, live space, and average block fill.
  • Device bytes per read, cold per request and warm per operation. This is the primary target.
  • Per-read counts and bytes at the server level, reported as full p50, p99, and max distributions.
  • Warm throughput, error rate, and read latency under both the SLO target and saturation.
  • CPU busy and iowait, and device utilization, to identify the bottleneck.
  • Rewrite wall time as a one-time conversion cost.
  • Read correctness at scale and unit-level round-trip correctness.

8. Findings

The win is bytes per read, not read-op count. Device reads per request near 2 to 3, the Data.db 1 plus Index.db 2 split, and server read_iops at p50 2 are all independent of chunk size. Every arm issues the same handful of reads. Fixed-output changes the bytes each read moves. Device bytes per operation fall 57% at S=16 under load.

The on-disk cost and the read-byte win trade off through S. Smaller S reads fewer bytes and costs more on disk. Larger S costs less on disk and reads more bytes. The on-disk cost comes from two sources that were separated by measurement. Padding was the packer's accept threshold and per-flush short blocks, which the tightening removed. The remaining cost at small S is compression context, since a smaller chunk gives Zstd a smaller window.

Throughput on this machine is CPU-bound and equal across arms, because the client and server share the cores and the device stays about half utilized. On a device-bound machine the byte savings would show as throughput. Here they show as headroom, visible in the saturation error rate that stays at zero for the smaller-S arms and rises for legacy and the larger-S arms.

9. Recommendation

S=32 is the balanced default. It costs 0.7% more on disk and cuts device bytes per operation by 32%, with a lower error rate than legacy under load. S=16 is the choice when the read-byte reduction is the priority, at 57% fewer device bytes and 7.6% more on disk. Pairing S=16 with a trained Zstd dictionary would recover most of that on-disk cost. S=48 is a point that beats legacy on both storage and device at once, 1.8% smaller on disk and 6 to 7% fewer device bytes, with a modest read win. S=64 should be avoided for point reads, since it over-fetches 19% more than legacy and has the worst error profile under load.

10. Correctness and verification

  • Unit tests pass for the fixed-output write and read round trip across incompressible, compressible, and sub-chunk sizes, for the streaming compressBounded contract, and for the streaming receiver. The Zstd, dictionary, and general compressor suites pass.
  • A deep review of the write path, metadata, and reader was run and its findings were addressed.
  • Reads return correct data end to end at 200 GB scale across the key range, on the standard buffered path and on the io_uring direct path.
  • The benchmark results were checked by an adversarial verification pass that cross-checked every metric against the raw traces, flagged overloaded runs, and confirmed which metrics are robust.

11. Caveats and limitations

  • The typical per-query read count is 2, measured as read_iops p50. The tail reaches 8 to 10 for keys spread across sstable generations or keys landing far from a Summary sample.
  • The bytes_decompressed histogram p50 is a reservoir or recording artifact. It reads 0 for some arms including legacy under warm load, so it is not trusted and is not fixed-output-specific.
  • Cold device bytes per request are read-ahead-inflated and quantized to 16 KB pages. The clean cold signal is VFS bytes per request, which equals S plus 16.
  • Throughput and latency are CPU-bound and run-variable. Legacy SLO measured 61.6 k in the final run and 52.4 k in an aborted earlier run at the same config.
  • The streaming override reduces recompression to about one pass per chunk but did not reduce rewrite wall time, which is dominated by per-chunk context setup and total compression work.
  • The chunk_cache per-read histograms are unwired and the chunk cache is off in this configuration, so they read 0 and are excluded.

12. Remaining work

  • Trained Zstd dictionary support for fixed-output, to recover the small-S on-disk cost. The compress and decompress legs compose today. The training input stage needs the SSTableChunkSampler to read the fixed-output block layout.
  • Resolve the bytes_decompressed recording so the metric is usable.
  • Phase 4 residual hardening. The mmap reader falls back to the standard reader for fixed-output rather than using an mmap stride, resetAndTruncate across a flush boundary is unsupported, and a repair and bootstrap dtest remains to be run.
  • Confirm the throughput win on a device-bound machine, where the byte savings would raise throughput rather than headroom.
